## 1 引言

本文档给出系统三个层面的落地细节：

1. **数据库详细设计**：19 张表逐字段说明（字段名与 prisma/schema.prisma 严格一致）；
2. **API 详细设计**：按 worklog.md 既定契约逐接口给出 请求/响应/逻辑/涉及表；
3. **关键业务逻辑、前端页面与移动端页面**的详细设计。

约定：接口统一返回 `{ ok, data, message }`（见 02-概要设计 6.2），下文响应示例直接给出 `data` 内容；日期为 ISO 8601 字符串；错误响应 `{ "ok": false, "message": "...", "code": 4xx }`。

## 2 数据库详细设计

> 字段名/类型/默认值与 `prisma/schema.prisma` 完全一致。类型列标注 Prisma 类型；"约束"列含主键/唯一/默认/可空与自动行为。

### 2.1 系统域

#### 2.1.1 User（用户）

系统账号表，承载 7 类角色。登录名全局唯一，演示环境默认口令 123456。

| 字段 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| id | String | 主键 | PK，cuid 自动生成 |
| username | String | 登录用户名 | 唯一（@unique），必填 |
| password | String | 登录密码 | 默认 `"123456"`；生产环境必须哈希存储 |
| name | String | 姓名（界面展示名） | 必填 |
| role | String | 角色代码 | 必填；ADMIN/MANAGER/ENGINEER/REVIEWER/OPERATOR/GUARDIAN/ACCEPTOR |
| department | String? | 所属部门/车间 | 可空 |
| phone | String? | 手机号 | 可空 |
| active | Boolean | 是否启用 | 默认 true；false 禁止登录 |
| createdAt | DateTime | 创建时间 | 默认 now() |
| updatedAt | DateTime | 更新时间 | @updatedAt 自动维护 |

### 2.2 台账域

#### 2.2.1 BlindPlate（盲板实体）

一板一码的盲板全生命周期台账。

| 字段 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| id | Int | 主键 | PK，自增 |
| code | String | 盲板编号 | 唯一（@unique），格式 MB-规格-NNNN，如 MB-DN50-0001 |
| spec | String | 规格 | 必填，字典 BLIND_SPEC，如 DN50 |
| type | String | 类型 | 必填，字典 BLIND_TYPE：八字盲板/插板/垫环/盲法兰 |
| material | String | 材质 | 必填，字典 MATERIAL：Q235B/Q345R/304/316L/20# |
| thickness | Float | 厚度（mm） | 必填，如 8/10/12 |
| pressureRating | String | 压力等级 | 必填，字典 PRESSURE：PN1.0/PN1.6/PN2.5/PN4.0/PN6.3 |
| status | String | 盲板状态 | 默认 `"IN_STOCK"`；IN_STOCK 在库 / RESERVED 已预留 / INSTALLED 已安装 / SCRAPPED 已报废 |
| location | String? | 当前位置 | 在库=库位（如"盲板库-A区-1排1架"）；已安装=装置+管线位置；预留="已预留待领用"；报废="报废区" |
| unitId | Int? | 所属装置（当前安装地） | 可空；在库/预留时为空，安装时=需求装置 |
| createdAt | DateTime | 创建（入库）时间 | 默认 now() |
| updatedAt | DateTime | 更新时间 | @updatedAt 自动维护 |

#### 2.2.2 InventoryItem（盲板库存）

按"规格+类型+材质"聚合的库存与预警线，与 BlindPlate 无外键（派生聚合+虚拟盘点行）。

| 字段 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| id | Int | 主键 | PK，自增 |
| spec | String | 规格 | 必填 |
| type | String | 类型 | 必填 |
| material | String | 材质 | 必填 |
| quantity | Int | 在库数量 | 默认 0；不允许负数 |
| minQuantity | Int | 最低库存（预警线） | 默认 2；quantity < minQuantity 触发低库存预警 |
| updatedAt | DateTime | 更新时间 | @updatedAt 自动维护 |

#### 2.2.3 ChangeRecord（盲板变动记录）

| 字段 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |

| workCode | String? | 关联作业票/需求编号 | 可空，如 WR-202506-001 或 BP-202506-001 |
| location | String? | 涉及位置 | 可空（安装位置或库位） |
| fromStatus | String? | 变动前状态 | 可空 |
| toStatus | String? | 变动后状态 | 可空 |
| operator | String | 操作人姓名 | 必填 |
| note | String? | 备注 | 可空 |
| createdAt | DateTime | 发生时间 | 默认 now() |

## 3 API 详细设计

> 与 worklog.md API 契约一一对应，接口共 16 组。权限列见 02-概要设计 8.2；"联动"列描述状态机与跨表副作用。

### 3.0 通用说明

- 分页：列表接口本版本不强制分页（数据量可控），变动记录用 `?limit=100`；
- 命名：`[id]` 为路由参数（Next.js 动态段 `src/app/api/xxx/[id]/route.ts`）；
- 服务端校验失败返回 400 并给出中文 message；状态前置校验不通过示例：`{ "ok": false, "message": "当前状态不允许该操作", "code": 400 }`。

### 3.10 工艺处置方案（与 3.9 同构）

- `GET/POST /api/disposal-schemes?workRequestId=`：POST 校验需求 status=ISOLATION_APPROVED，生成 **GY-** 编号，创建方案+steps（method/detail/standard），需求 → DISPOSAL_PREPARING；
- `PUT /api/disposal-schemes/[id]`：steps 整体替换；仅 DRAFT/REJECTED 可编辑；
- `POST /api/disposal-schemes/[id]/submit`：方案→PENDING_REVIEW，需求→DISPOSAL_PENDING_REVIEW，留痕（bizType=DISPOSAL）；
- `POST /api/disposal-schemes/[id]/review`：approve=true → 方案 APPROVED、需求 DISPOSAL_APPROVED；approve=false → 方案 REJECTED、需求 DISPOSAL_REJECTED（comment 必填）；
- 处置步骤执行勾选：`PUT /api/disposal-schemes/[id]/steps`（设计约定接口，可选）或并入 PUT：APPROVED 方案下按 stepId 更新 completed 布尔；
- 涉及表：DisposalScheme、DisposalStep、ApprovalRecord、WorkRequest。

## 4 关键业务逻辑详细设计

### 4.1 编号生成规则

| 前缀 | 对象 | 规则 | 示例 |
| --- | --- | --- | --- |
| WR- | 作业需求 | WR-YYYYMM-NNN，按月流水 3 位 | WR-202506-001 |
| GL- | 隔离方案 | GL-YYYYMM-NNN | GL-202506-001 |
| GY- | 工艺处置方案 | GY-YYYYMM-NNN | GY-202506-001 |
| BP- | 作业票 | BP-YYYYMM-NNN | BP-202506-001 |
| TSK- | 作业任务 | TSK-YYYYMM-NNN | TSK-202506-001 |
| MB- | 盲板实体 | MB-规格-NNNN，全局流水 4 位（按规格段独立递增） | MB-DN150-0001 |

生成算法（服务端、事务内）：

```text
function nextCode(prefix, scope):        // scope: 年月（WR/GL/GY/BP/TSK）或 规格（MB）
  ym  = now().format("yyyyMM")           // MB 时为 spec
  pat = prefix + "-" + ym + "-"
  last = 表内 code startsWith(pat) 按 code 倒序取第一条
  seq  = last ? parseInt(last 去前缀后的数字段) + 1 : 1
  return pat + String(seq).padStart(3, "0")   // MB 为 padStart(4,"0")
```

并发与一致性处理：

1. 编号生成与单据创建放入同一事务；MySQL 生产环境对"取最大流水"语句加 `SELECT ... FOR UPDATE`（按前缀维度串行化），SQLite 沙箱单写连接天然串行；
2. 唯一约束兜底：code 列均有 @unique，插入冲突（P2002）时整体重试一次（重新取号）；
3. 按月重置流水，便于人工按月对账；需求删除不回收编号（流水中断可接受，禁止复用）。

### 4.2 盲板状态联动逻辑

盲板状态机（`BlindPlate.status`）与业务动作矩阵：

```text
                reserve(预留)          execute(ADD 执行安装)      execute(REMOVE 执行拆除)
IN_STOCK ──────────► RESERVED ────────────► INSTALLED ────────────────► IN_STOCK
    │                    │                      │                          ▲
    │  PURCHASE(入库)    │                      │  SCRAP(报废,仅ADMIN)      │
    ▼                    ▼                      ▼                          │
 (新增实体)          SCRAP 禁止               SCRAPPED ◄───────────────────┘
```

| 业务事件 | 触发接口 | fromStatus | toStatus | location 变化 | ChangeRecord.action | 附加 |
| --- | --- | --- | --- | --- | --- | --- |
| 采购/新增入库 | POST /api/blind-plates | （无） | IN_STOCK | 库位 | PURCHASE | — |
| 隔离点预留绑定 | POST /api/isolation-points/[id]/reserve | IN_STOCK | RESERVED | →"已预留待领用" | RESERVE | 点.blindPlateId 绑定 |
| 加装点执行 | POST /api/isolation-points/[id]/execute（action=ADD） | RESERVED | INSTALLED | →"装置名+隔离位置"（unitId=需求装置） | INSTALL | 点 done=true |
| 拆除点执行 | 同上（action=REMOVE） | INSTALLED | IN_STOCK | →库位（回收区/原库位），unitId=null | REMOVE | 点 done=true；建议同步 InventoryItem.quantity+1 |
| 报废 | PUT /api/blind-plates/[id]（status=SCRAPPED） | IN_STOCK 或 INSTALLED | SCRAPPED | →"报废区" | SCRAP | — |
| 归还入库（手工/盘盈） | POST /api/inventory/[id]/adjust(delta>0) | —（聚合层） | IN_STOCK | — | RETURN/PURCHASE | 聚合数量+ |
| 需求取消释放 | POST /api/work-requests/[id]/cancel | RESERVED | IN_STOCK | →原库位 | RETURN（note=需求取消自动释放） | 解除点绑定 |

联动硬约束：

1. **每次状态变化必须写 ChangeRecord**，fromStatus/toStatus 必填、operator 必填——台账流水是 HSE 审计证据，禁止静默改库；
2. RESERVED 状态的盲板不可再被其他隔离点预留（候选列表过滤 status=IN_STOCK）；
3. INSTALLED 盲板不可编辑规格/材质/类型（必须先走拆除流程）；
4. 库存聚合（InventoryItem）以 IN_STOCK 实体为准定期校准；预留/安装不扣减聚合库存（聚合口径=物理在库），拆除归还时 +1（若实现该同步，需与 adjust 接口幂等）。

### 4.3 执行隔离点作业联动（isolation-points/[id]/execute 完整逻辑）

```text
POST /api/isolation-points/[id]/execute  { operator: "王班长" }

1. 事务开启（db.$transaction）
2. 读取链路: point → scheme → workRequest
   2.1 point 不存在 → 404
   2.2 point.done === true → 幂等返回当前状态（200，不重复写流水）
   2.3 workRequest.status ∉ {TICKET_APPROVED, IN_PROGRESS} → 400 "作业票批准后方可执行隔离点作业"
3. 分支处理（按 point.action）:
   3.1 action = ADD（加装盲板）:
       a. 校验 point.blindPlateId 非空（为空 → 400 "请先预留绑定盲板"）
       b. 校验盲板.status === RESERVED（否则 400 "盲板状态异常，无法安装"）
       c. 盲板更新: status=INSTALLED
                   location = `${workRequest.unit.name}-${point.location}`
                   unitId   = workRequest.unitId
       d. 写 ChangeRecord: action=INSTALL, blindCode=盲板.code,
          workCode=ticket?.code ?? workRequest.code,
          location=新 location, fromStatus=RESERVED, toStatus=INSTALLED,
          operator=请求体.operator, note="按隔离方案加装盲板"
   3.2 action = REMOVE（拆除盲板）:
       a. 校验 point.blindPlateId 非空（拆除点在方案编制期即绑定在装盲板）
       b. 校验盲板.status === INSTALLED（否则 400 "盲板不在安装状态，无法拆除"）
       c. 盲板更新: status=IN_STOCK
                   location = "盲板库-回收区"（归还库位，unitId=null）
       d. 写 ChangeRecord: action=REMOVE, …, fromStatus=INSTALLED, toStatus=IN_STOCK,
          operator, note="按隔离方案拆除盲板并归还"
4. 隔离点勾选: point.done=true, point.doneAt=now(), point.operator=请求体.operator
5. 聚合进度: total=方案下点数, done=done=true 计数
   （若全部完成，可在响应 message 提示"隔离点已全部执行完成，可申请验收"）
6. 事务提交，返回 { point, blindPlate, changeRecord, progress }
7. 异常回滚：任何一步失败整体回滚（盲板状态、流水、点勾选三者强一致）
```

幂等与并发：done 已为 true 时直接返回（步骤 2.2）；同一秒并发重复点击由事务 + done 状态检查串行化；流水以"点"为粒度一人一条。

### 4.4 审核驳回回退逻辑

| 场景 | 驳回前 | 驳回后（单据） | 驳回后（需求） | 恢复路径 |
| --- | --- | --- | --- | --- |
| 隔离方案审核驳回 | 方案 PENDING_REVIEW / 需求 ISOLATION_PENDING_REVIEW | 方案 REJECTED（comment 必填，reviewedBy/At 记录） | ISOLATION_REJECTED | 编制人 PUT 修改 points（整体替换）→ 重新 /submit → 需求回 ISOLATION_PENDING_REVIEW；每次提交/驳回均写 ApprovalRecord |
| 工艺处置方案审核驳回 | 方案 PENDING_REVIEW / 需求 DISPOSAL_PENDING_REVIEW | 方案 REJECTED | DISPOSAL_REJECTED | 同上（steps 整体替换→重提） |
| 作业票审批驳回 | 票 PENDING_REVIEW / 需求 TICKET_ISSUED | 票 VOID（作废，票号不复用） | CONFIRMED | 修改票面信息后重新 POST /api/work-tickets 生成新票（新 BP- 号）→ 重新签发/批准 |
| 工艺处置确认不合格 | —（确认单 result=UNQUALIFIED） | 确认单保留（可 upsert 覆盖） | 保持 PENDING_CONFIRM | 现场整改处置 → 重新 POST /api/disposal-confirmations，result=QUALIFIED → CONFIRMED |
| 验收整改复验 | —（验收单 conclusion=RECTIFY） | 验收单保留 problems | 保持 PENDING_ACCEPTANCE | 整改完成后重新 POST /api/acceptances 覆盖（upsert），PASS → COMPLETED |

回退通用规则：

1. 驳回一律留痕（ApprovalRecord.action=REJECT + comment），需求与子单据状态同步更新在同一事务；
2. REJECTED 状态的方案禁止直接编辑为 APPROVED（必须走 submit→review 闭环）；
3. 作业票作废（VOID）为终态，不可"复活"；重新开票产生新编号，审批历史通过需求详情时间线串联。
